Decision Engineering is the discipline of building reliable decision systems out of unreliable decision-makers.

Humans forget things, misunderstand context, make inconsistent judgments, and change their minds. Agents hallucinate, lose context, reason differently across runs, and confidently produce incorrect outputs.

If we require every human or agent to be perfectly reliable, the system will fail.

So Decision Engineering takes the same approach that reliable software systems take:

Assume components will fail. Design the system so those failures are contained, detectable, and recoverable.

### The analogy to software reliability

Imagine a distributed system.

Individual machines can crash. Packets can disappear. Processes can return errors. Databases can temporarily disagree.

We don't solve this by saying:

> "Let's build a computer that never crashes."

Instead, we introduce mechanisms such as replication, checksums, transactions, retries, isolation, monitoring, and well-defined interfaces.

The **system** becomes much more reliable than any individual component.

Decision Engineering can do the same thing for reasoning.

The unreliable components are:

**Human**\
→ forgets context\
→ makes implicit assumptions\
→ changes interpretation\
→ makes mistakes

**Agent**\
→ hallucinates\
→ retrieves the wrong context\
→ follows stale instructions\
→ behaves nondeterministically

DE puts a reliability layer around them.

### 1. Make decisions explicit

Without DE:

> Agent thinks price should be $49 → updates website.

The reasoning disappears.

With DE:

**Facts → Decision → Output Fact**

For example:

**Facts**

- CAC = $35
- target payback &lt; 2 months
- gross margin = 85%

↓

**Decision**\
Set subscription price to $49.

↓

**Output fact**\
`product.monthly_price = $49`

Now another agent doesn't need to reproduce the original reasoning from scratch.

This is similar to **persisting state instead of relying on process memory**.

---

### 2. Give every decision a contract

A decision shouldn't just contain its answer.

It should say what must be true for that answer to remain valid.

For example:

> Price = $49\
> provided CAC &lt; $40\
> and gross margin &gt; 80%.

Those are the decision's **invariants**.

Now an agent can make mistakes, but the system can check:

> "Does the resulting state violate an invariant?"

This is analogous to assertions, type systems, schemas, database constraints, or API contracts.

You don't trust the program.

You **verify its output against a contract**.

---

### 3. Localize failures

This is perhaps the most important principle.

Suppose pricing changes.

Without boundaries:

```
Pricing agent
   ↓
website
   ↓
marketing
   ↓
forecast
   ↓
sales
   ↓
customer emails
```

One wrong decision can propagate everywhere.

Instead:

```
Facts
  ↓
Pricing Decision
  ↓
monthly_price = $49
  ↓
──────────────
 consumers
──────────────
Website
Forecast
Marketing
Billing
```

Pricing owns exactly one authoritative output:

> `monthly_price`

Everyone else consumes it.

If pricing is wrong, you know where to look.

You don't have to inspect the entire company.

That's **fault isolation**.

---

### 4. Separate deciding from acting

This is especially important with agents.

An agent saying:

> "I think we should reduce the price."

should not automatically mean:

> website changed\
> Stripe changed\
> ads changed\
> customers notified.

Instead:

```
Agent proposes
      ↓
Decision recorded
      ↓
Verification
      ↓
Authoritative fact updated
      ↓
Consumers react
```

This introduces a boundary between **reasoning** and **side effects**.

Very similar to the programming principle we discussed earlier.

---

### 5. Preserve provenance

When something looks wrong, the system should be able to answer:

```
Why is the price $49?

Because Decision D-142 set it.

Why did D-142 make that decision?

Because:
CAC = $35
margin = 85%
target payback = 2 months
```

So instead of:

```
Current state
```

you have:

```
Current state
     ↑
Decision
     ↑
Facts
```

That gives you a causal debugging path.

It's essentially **observability for decisions**.

---

### 6. Detect disagreement rather than hiding it

Suppose two agents reach different conclusions.

Agent A:

> Price should be $49.

Agent B:

> Price should be $39.

A naive multi-agent system might simply ask another model to choose.

DE asks something more useful:

```
Which fact differs?
Which assumption differs?
Which objective differs?
Which policy differs?
```

Perhaps:

```
Agent A assumes CAC = $35
Agent B assumes CAC = $18
```

Now the disagreement has been localized to a fact.

That's far easier to resolve.

---

### 7. Make recovery cheap

A reliable system isn't one that never fails.

It's one where failure is cheap to correct.

Suppose CAC changes:

```
CAC
$35 → $70
```

The system should know:

```
CAC
 ↓
Pricing Decision
 ↓
monthly_price
 ↓
Forecast
Billing
Marketing
```

You don't need an agent to reread the entire company history.

You recompute the affected decisions.

This is analogous to dependency graphs in spreadsheets, build systems, or reactive programming.
